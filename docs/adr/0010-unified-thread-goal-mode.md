# ADR 0010：统一工作线程与渐进式目标模式

## 状态

已接受，2026-07-29。部分取代 ADR 0009 中“对话与任务作为两个一级工作区”的决策。

## 背景

`Conversation` 和 `WorkItem` 在领域层承担不同职责：前者保存消息上下文，后者聚合目标、
Run、审批、权限和 Artifact。该边界对于恢复、审计和自动化是必要的。

旧 GUI 将这两个领域对象直接映射为“对话”和“任务”两个竞争入口，同时又把新建对话、
标题和 Composer 文案称为“任务”。用户需要在目标尚未清晰时先决定使用哪套界面，
对话发展为复杂工作后也缺少保留历史的升级路径。

## 决策

1. 对话是唯一内容入口和历史容器；简单问答与复杂工作都从同一线程开始。
2. `WorkItem` 作为对话的可选目标状态，不与 `Conversation` 合并。
3. 用户可以把当前对话原地设为目标；升级必须复用 `conversation_id` 和已有消息。
4. 目标对话的后续 Turn 使用 `RunType.WORKFLOW` 并携带 `work_item_id`。
5. 每次目标执行完成后，仍由 WorkItemService 根据最新 Run 固化 Artifact。
6. 原任务中心改为“工作概览”，只负责跨对话聚合状态、审批、自动化结果和交付物。
7. 工作概览直接新建目标时，必须同时创建对应对话，避免孤立 WorkItem。
8. `Run`、checkpoint、ActionProposal 和 EffectRecord 继续作为按需展开的执行事实。

## 结果

- 用户无需在“聊天还是任务”之间预先分类。
- 普通对话可以在需求明确后无损升级为可恢复、可验收的目标。
- 最近对话继续是主要导航；工作概览成为行动队列，而非第二套消息产品。
- 后端可靠执行、幂等、自动化系列和 Artifact 模型保持兼容。
- `WorkItemKind.CHAT` 暂时保留用于数据兼容，但普通 GUI 对话不会因此创建 WorkItem。

## 后续

- 在目标进度条加入状态驱动的暂停、恢复和编辑目标能力。
- 支持运行中安全点的后续指令，而不仅是终态追加要求。
- 增加 Project 分组、Chat 归档、固定和分叉。
- 将自动化结果与跨对话审批汇总到统一收件箱。
